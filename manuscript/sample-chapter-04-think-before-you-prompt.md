# Sample Chapter — Think Before You Prompt

## Chapter 4. Think Before You Prompt

Prompting is now mistaken for thinking.

Part II starts upstream: define the work before you ask for output. The next chapters turn that definition into workflow, ownership, and standards. If this first move is weak, the rest of the system only scales confusion faster.

This chapter is not about prompt tricks. It is about work definition.

Used well, AI helps a clear mind move faster. Used badly, it helps confusion move faster. The difference is not mainly phrasing. It is whether the person using the tool has defined the job clearly enough to own it.

When people say they need to “get better at prompting,” they are often naming the wrong bottleneck. The bottleneck is usually not phrasing. It is problem definition. The model is being asked to operate on work that has not yet been properly framed. The result is predictable: plausible output attached to blurry intent.

So the first high-agency habit in AI-assisted work is not “ask better.” It is “define the work before you ask.”

## The wrong way to start AI-assisted work

Weak AI use often begins with speed pressure.

A manager needs a memo by noon. A strategist needs a recommendation before a meeting. A researcher needs to get up to speed quickly. A team lead needs a cleaner status update. Instead of clarifying the job, they push the ambiguity straight into the model.

The request sounds reasonable:
- summarize this,
- write a draft,
- make this more strategic,
- turn this into a plan,
- give me recommendations,
- make this sound executive-ready.

The model responds well enough to keep the workflow moving. That is exactly why this pattern is dangerous.

It creates five recurring failures.

### 1. The deliverable replaces the problem
The person asks for a memo, deck, summary, or plan before defining what the artifact is supposed to solve. The work becomes about producing the document rather than resolving the underlying issue.

### 2. The output sounds finished before the thinking is ready
AI is good at producing organized language. That can make half-formed thinking look complete. Once the artifact exists, people become reluctant to reopen the framing underneath it.

### 3. Quality remains implicit
If “good” is never defined, the model defaults to something safe: balanced, fluent, generic, and often forgettable. The output may be usable enough to pass along and too weak to do the real job.

### 4. Hidden constraints show up too late
The first draft may ignore timing, audience, risk tolerance, internal politics, compliance limits, missing evidence, or tone requirements because none of that was made explicit before generation began.

### 5. Stakes disappear behind polish
The model cannot care more than the operator does. If the user has not named what matters — reputational risk, trust, decision quality, cost of error, human consequences — the output will usually treat the work as lower-stakes than it really is.

These are not prompt-quality failures. They are work-definition failures.

## The first operating discipline: define the work before generating anything

Before you generate, write a brief.

Not a long brief. Not a ceremonial brief. A short working brief that makes the job concrete enough for a model to assist without silently deciding the shape of the work for you.

This chapter uses a simple pre-generation grammar:

1. **Problem**
2. **Objective**
3. **Standard**
4. **Constraints**
5. **Stakes**

That grammar travels across domains. It works before drafting, research, planning, or coordination because it makes the work legible before a system starts accelerating it.

If you only remember one practice from this chapter, make it this:

**Do not start with the request. Start with the brief.**

## The reusable pre-generation grammar

Each part of the grammar solves a different failure.

### 1. Problem — What is actually going on?

The problem is the real situation, not the artifact you think you need.

This is where people often go wrong first. They say the problem is “I need a presentation,” “I need an email,” or “I need a summary.” Those are tasks. The problem sits underneath them.

Examples:
- Not “I need a memo.”  
  Better: “Leadership is split on whether to narrow scope, and the disagreement is still hiding behind vague status language.”
- Not “I need research.”  
  Better: “I do not yet understand which variables actually matter for this decision.”
- Not “I need meeting notes.”  
  Better: “Different people left the meeting with different assumptions, and we need one accountable record of what changed.”

The problem statement should answer:
- What is happening?
- What is unclear, unresolved, or at risk?
- Why is the current state insufficient?

Concrete rule: if your “problem” can be solved merely by producing a prettier artifact, you probably have not named the real problem yet.

### 2. Objective — What should this work accomplish?

The objective is the change you want the work to create.

This matters because a summary, draft, or analysis can be excellent on its own terms and still fail the job. A clean document is not automatically a useful document. The objective forces you to define what the artifact is supposed to do in the world.

Examples:
- clarify a decision for leadership,
- prepare a team for a difficult tradeoff,
- surface the strongest options before commitment,
- identify what still needs verification,
- create an accountable handoff,
- persuade a reader to approve, align, reconsider, or act.

The objective should answer:
- What should be clearer after this?
- What decision, action, or understanding should become possible?
- What will this output help someone do?

Concrete rule: write the objective as a change in the reader, team, or decision state — not as a request for content.

### 3. Standard — What does good look like here?

The standard is your definition of acceptable quality.

Without a standard, the model will usually optimize for plausibility. That is rarely enough. In professional work, “good” might mean concise, evidence-aware, decision-ready, non-defensive, specific, audience-appropriate, or explicit about uncertainty. Different jobs require different standards.

The standard should answer:
- What qualities must this output have?
- What would make you trust it?
- What would make it unusable even if it sounds polished?

Useful standards include:
- specific rather than generic,
- decision-ready rather than merely informative,
- candid rather than overly diplomatic,
- structured enough to act on,
- honest about uncertainty,
- faithful to source material,
- suitable for the actual audience.

Concrete rule: if two people could look at the output and disagree wildly about whether it is good, your standard is still too vague.

### 4. Constraints — What limits are real?

Constraints are the boundaries the work has to respect.

This includes obvious limits like length and deadline, but the more important constraints are often strategic:
- do not overstate certainty,
- stay within known evidence,
- do not create legal or reputational exposure,
- do not embarrass another team unnecessarily,
- keep the tone calm,
- fit the decision-making time available,
- avoid implying approval that has not been given,
- stay compatible with existing commitments.

Constraints should answer:
- What must this work stay inside?
- What is non-negotiable?
- What should the output avoid doing?

Concrete rule: if you discover the most important boundary only after the first draft, you started too early.

### 5. Stakes — Why does this matter?

Stakes define the cost of getting the work wrong.

This is the part people omit most often, and it is one of the most important. Stakes help determine how much rigor, caution, review, and human involvement the work deserves.

Examples:
- a weak draft could mislead leadership into choosing the wrong priority,
- a vague recap could create false alignment across teams,
- a shallow research summary could produce overconfidence,
- a generic message could damage trust with a sensitive audience,
- a sloppy framing could make the team solve the wrong problem for a week.

Stakes should answer:
- What happens if this output is wrong, thin, or misleading?
- Who bears the cost?
- What kind of failure is most dangerous here?

Concrete rule: the higher the stakes, the less acceptable it is to let fluency stand in for judgment.

## Turn the grammar into a one-minute pre-generation brief

The point of the grammar is not theory. It is operational clarity.

Before you ask AI for substantial output, write five lines:

- **Problem:**  
- **Objective:**  
- **Standard:**  
- **Constraints:**  
- **Stakes:**  

That is enough.

It should be plain language, not performance. If you cannot write those five lines, that is useful information. It means the work is still underdefined, and AI will likely amplify the confusion rather than resolve it.

This brief does three things at once:

1. It clarifies the job for you.
2. It determines whether AI should be used yet, and for what.
3. It creates a review frame for judging whatever comes back.

That last point matters.

Most people review AI output against a weak question: “Does this sound good?”

A stronger question is: “Does this solve the problem, achieve the objective, meet the standard, respect the constraints, and handle the stakes honestly?”

That is a much harder test. It is also the test that produces trustworthy work.

## How to use the brief before you generate

The point is not to pause vaguely. It is to do the specific upstream work that makes generation useful.

### Step 1. Separate the situation from the artifact

First describe the situation in reality. Then decide whether an artifact is the right next move.

Sometimes the right next move is not “generate a draft.” It is:
- identify the real decision,
- gather missing evidence,
- resolve a disagreement,
- define the audience,
- or decide what remains human-owned.

If you skip this step, you risk using the model to produce an answer-shaped object for a question that is still unstable.

### Step 2. Write the five-part brief

Use the pre-generation grammar in order:
- problem,
- objective,
- standard,
- constraints,
- stakes.

Do not write an essay. Write a working brief. If one of the five lines feels weak, pause there. The weak line is usually the source of the downstream quality problem.

Practical rule:
- weak problem -> wrong task
- weak objective -> irrelevant output
- weak standard -> generic output
- weak constraints -> unusable output
- weak stakes -> careless workflow

### Step 3. Decide what AI should and should not do

Only after the brief exists should you decide the role of the model.

Should AI:
- propose structures,
- generate options,
- compress material,
- surface likely objections,
- compare alternatives,
- draft a first pass,
- or help diagnose weaknesses?

And what should remain human-owned?
- the framing,
- the decision,
- the tone,
- the final recommendation,
- the judgment about evidence,
- or the acceptance of risk?

This is the moment where high-agency work stops AI from quietly taking over the wrong part of the job.

### Step 4. Generate only at the level the work is ready for

Do not ask for a final-form artifact if the brief is still incomplete.

If the problem is clear but the structure is not, ask for structure.
If the structure is clear but options are thin, ask for options.
If the options are clear but language is rough, ask for language.

Generation should follow clarity, not substitute for it.

Concrete rule: ask the model for the next useful layer of help, not the full polished answer by default.

### Step 5. Review against the brief, not against the polish

Once output exists, bring the five-part brief back into view.

Check:
- Did this actually address the stated problem?
- Does it move the objective forward?
- Does it meet the named standard?
- Did it violate a constraint?
- Is it calibrated to the stakes?

If the answer is no, the response is not “bad AI output.” It is either the wrong output for the brief or evidence that the brief still needs work.

That is a better debugging method than endlessly rewriting the request without examining the frame.

## A real-work scenario

Imagine an operations lead who has to prepare a one-page note for leadership after a rough week.

Customer response times have slipped. One team believes the issue is staffing. Another believes the issue is process design. Leadership wants an update before the afternoon meeting. The easy move is to ask AI:

“Write an executive update on our support situation.”

That request will likely produce something polished, balanced, and weak. It may mention efficiency, service quality, cross-functional collaboration, and next steps. It may sound responsible while helping no one decide anything.

A higher-agency start looks different.

First, the lead writes the pre-generation brief:

- **Problem:** Response times are slipping, leadership is hearing competing explanations, and the team does not yet have a shared view of the bottleneck.
- **Objective:** Give leadership a decision-ready update that clarifies what is known, what is still uncertain, and what short-term action should be taken this week.
- **Standard:** Specific, calm, honest about uncertainty, and structured so leadership can choose among concrete next moves.
- **Constraints:** One page; use only facts already confirmed internally; do not assign blame; do not imply root cause certainty that we do not yet have.
- **Stakes:** A vague or overstated update could send people after the wrong fix, damage trust across teams, and waste another week.

Now the role of AI becomes clearer.

The model could help:
- propose two or three possible structures for the note,
- turn scattered facts into a tighter sequence,
- surface what leadership will likely ask next,
- or produce a first draft once the framing is locked.

But the model should not decide:
- what the real problem is,
- whether the evidence is strong enough,
- which uncertainty should stay visible,
- or what action leadership should actually take.

That distinction changes the entire workflow.

Instead of accepting the first polished update, the operations lead can use AI to support a more serious process:
1. clarify the problem,
2. structure the note,
3. test whether the note makes the uncertainty visible,
4. revise until the artifact matches the brief,
5. then send something leadership can actually use.

This is not slower in the way that matters.

It may delay generation by a few minutes. It prevents hours or days of downstream confusion.

## Why this chapter sits first in Part II

The five-part brief sits upstream of the rest of Part II. It forces the job to become legible before drafting, research, planning, or coordination begin.

The domains change. The discipline does not. That is why this chapter comes first.

## Where people still get into trouble

Even after learning the grammar, people tend to make the same mistakes.

The first is naming the artifact instead of the problem.

The second is writing objectives that are really formatting instructions.

The third is using standards that mean almost nothing: “make it good,” “make it strategic,” “make it more polished.”

The fourth is treating constraints as purely cosmetic: word count, format, tone — while ignoring more important boundaries like evidence limits, political reality, decision timing, or reputational risk.

The fifth is leaving stakes out because naming them feels heavy. But unnamed stakes do not disappear. They simply stop guiding the workflow.

The sixth is forgetting that the brief is also a review tool. A pre-generation brief is wasted if you never use it to judge the output that followed.

The antidote is simple:

If the output feels wrong, inspect the brief before you blame the wording.

## A practical checklist for thinking before you prompt

Before you generate anything:
- What is the actual problem, beneath the artifact request?
- What should this work make possible?
- What does good look like here?
- What limits are real?
- What is at stake if this is wrong, generic, or misleading?

Before you decide AI’s role:
- Is the work defined well enough to accelerate?
- Should AI help with structure, options, compression, critique, or drafting?
- What part of this task must remain fully human-owned?

When reviewing the output:
- Did it solve the stated problem, or just produce language?
- Did it achieve the objective?
- Does it meet the named standard?
- Did it stay inside the constraints?
- Is the level of confidence appropriate to the stakes?

If the answer to several of those questions is no, do not keep polishing blindly. Reframe the job.

## The deeper point

Thinking before you prompt is not a ritual for cautious people. It is the defining move of the work.

AI makes production cheap. That raises the value of workers who can still define the work well before production begins.

The professional advantage does not come from knowing how to ask a machine for more output than everyone else. It comes from knowing what the output is for, how good it needs to be, what must constrain it, and why the stakes deserve real care.

That is why prompting is downstream of clarity.

First define the problem.
Then name the objective.
Then set the standard.
Then mark the constraints.
Then make the stakes visible.

Only then should generation begin.

That is how AI becomes leverage instead of drift.

Once the work is defined, the next question is no longer “what prompt should I try?” It is “what repeatable workflow should carry this task next time?” That is the move into Chapter 5.
